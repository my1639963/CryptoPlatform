## 1. 总体实施路线图

按模块依赖关系划分为 **6 个开发阶段（Phase）**，每个阶段有明确的交付物和验收标准。

### Phase 1：基础设施与领域模型（第 1-2 周）

**目标**：搭建项目骨架、持久化层和领域核心模型，使后续开发有可编译的基础框架。

| 任务 | 交付物 | 涉及项目 |
|------|--------|----------|
| Solution / Project 创建 | 可编译的空 Solution | 全部 12 个项目 |
| NuGet 包安装 | 各 csproj 依赖完整 | — |
| Domain 实体 + 枚举 | Key/KeyVersion/状态机/值对象 | `CryptoPlatform.Domain` |
| EF Core Entity + Fluent API | 14 张表完整映射 | `CryptoPlatform.Persistence` |
| DbContext + DI 注册 | 可连接数据库的最小上下文 | `CryptoPlatform.Persistence` |
| 数据库 Migration（MySQL 8.4） | 首次迁移脚本，14 张表落地 | — |
| Serilog 日志框架接入 | 结构化日志输出到控制台+文件 | `CryptoPlatform.Api` |
| SaveChanges 拦截器 | `updated_at` 自动维护 | `CryptoPlatform.Persistence` |

**前置依赖**：无
**验收标准**：`dotnet build` 通过；`dotnet ef migrations add InitialCreate` 成功；数据库 14 张表创建完毕。
**预估工作量**：5-7 人天

---

### Phase 2：密码学 Provider 抽象层（第 3-4 周）

**目标**：完成 ICryptoProvider 接口体系和 SoftwareCryptoProvider（BouncyCastle）实现，使密码运算可在无 HSM 环境下运行。

| 任务 | 交付物 | 涉及项目 |
|------|--------|----------|
| ICryptoProvider 完整接口 | 接口 + 全部 DTO + 枚举 | `CryptoPlatform.Crypto.Abstractions` |
| ICryptoProviderRouter 接口 | 路由抽象 | `CryptoPlatform.Crypto.Abstractions` |
| SoftwareCryptoProvider | SM2/SM3/SM4/HMAC-SM3 全算法实现 | `CryptoPlatform.Crypto.Software` |
| ProviderRouter 默认实现 | 基于绑定/默认配置路由 | `CryptoPlatform.Crypto.Software` |
| Provider 单元测试 | 算法正确性 + 错误码 + 能力声明 | 测试项目 |

**前置依赖**：Phase 1（Domain 枚举定义）
**验收标准**：SM2 加密/解密/签名/验签、SM3 标准测试向量、SM4 各模式（ECB/CBC/CTR/GCM）、HMAC-SM3 全部通过已知答案测试（KAT）。
**预估工作量**：7-10 人天

---

### Phase 3：核心业务服务层（第 5-8 周）

**目标**：实现 KeyService、CryptoService、Authorization 三大核心服务，完成密钥全生命周期管理和密码运算能力。

| 任务 | 交付物 | 涉及项目 |
|------|--------|----------|
| IKeyService + KeyService | 创建/激活/轮换/禁用/撤销/销毁/导入/查询 | `CryptoPlatform.Application` |
| Saga 补偿事务 | Provider+DB 分布式操作容错 | `CryptoPlatform.Application` |
| IKeyAuthorizationChecker | Owner + 显式授权校验 | `CryptoPlatform.Authorization` |
| ICryptoService + CryptoService | SM2/SM3/SM4/HMAC 全运算接口 | `CryptoPlatform.Application` |
| 密钥状态机校验 | 14 条允许转换 + 4 条禁止转换 | `CryptoPlatform.Domain` |
| 密钥包装体系 | Root Key → KEK → DataKey 三层包装 | `CryptoPlatform.Crypto.Software` |
| 无 HSM Root Key 存储 | 加密密钥库文件 + 主密码 | `CryptoPlatform.Crypto.Software` |
| 核心服务单元测试 | 状态转换 + 授权校验 + 算法运算 | 测试项目 |

**前置依赖**：Phase 1（Persistence）+ Phase 2（Provider）
**验收标准**：密钥全生命周期（CREATED→ACTIVE→ROTATED→DESTROYED）流转正确；补偿事务覆盖 Provider 成功/DB 失败场景；CryptoService 所有算法通过端到端测试。
**预估工作量**：15-20 人天

### 3.4 核心领域层实现要点

#### 3.4.1 密钥状态机

```
实现位置：CryptoPlatform.Domain 中的 KeyStatusTransition 验证器

核心规则：
- 14 条允许转换（白名单模式）
- 4 条显式禁止：DESTROYED→任意、REVOKED→ACTIVE、EXPIRED→ACTIVE、ROTATED→ACTIVE
- 状态校验必须在每次生命周期变更前执行
- 状态转换必须产生审计记录
```

#### 3.4.2 Provider 抽象

```
实现位置：CryptoPlatform.Crypto.Abstractions

核心约束：
- ICryptoProvider 零外部依赖（纯接口项目）
- Provider 不自动从 HSM 降级到 Software
- 非幂等操作（GenerateKey/DestroyKey/Sign）UNKNOWN 状态不自动重试
- 幂等操作（Hash/Verify）可有限重试（最多 2 次）
- 超时层级：API(30s) > Application(15s) > Provider(5-10s)
```

#### 3.4.3 密钥包装体系

```
实现位置：CryptoPlatform.Crypto.Software

三层包装：
  Root Key → KEK → DataKey/EncryptedKeyMaterial

无 HSM 场景 Root Key 保护：
  Master Password → KDF(PBKDF2-HMAC-SM3, ≥600,000次) → Protection Key
  → SM4-GCM 加密 → Keystore File
  → 系统启动时管理员输入主密码加载
  → 进程退出时安全清除内存
```

#### 3.4.4 补偿事务（Saga 模式）

```
实现位置：CryptoPlatform.Application (KeyService)

场景：Provider 成功 + DB 失败
流程：
  1. 记录 ProviderKeyRef 到补偿任务表
  2. CompensationWorker 重试 DB 写入（最多 3 次，指数退避）
  3. 重试失败 → Provider.DestroyKeyAsync 销毁孤儿密钥
  4. 销毁失败 → 产生 SECURITY_EVENT (CRITICAL)
  5. 绝不将孤儿 ProviderKeyRef 返回给业务系统
```

## 4. 关键实现规范摘要（开发约束清单）

以下约束从设计文档中提取，开发时必须严格遵循：

### 4.1 安全红线（不可违反）

| 编号 | 约束 | 来源 |
|:----:|------|------|
| S-01 | 密钥材料不得通过普通业务接口返回 | 详细设计 1.1 |
| S-02 | 私钥、SM4 密钥、HMAC 密钥不得离开密码服务平台安全边界 | 详细设计 1.1 |
| S-03 | KeyType、KeyUsage、OwnerAppId 创建后不可修改 | 详细设计 1.1 |
| S-04 | 所有生命周期变化必须产生不可篡改审计记录 | 详细设计 1.1 |
| S-05 | 密钥销毁必须具备二次确认 + 权限校验 + 销毁结果验证 | 详细设计 1.1 |
| S-06 | Root Key 不得以数据库明文保存 | 详细设计 1.6.2 |
| S-07 | HSM 私钥明文、SM4/HMAC 对称密钥明文、AppSecret 明文、Access Token 明文禁止存储于日志 | 核心模块 1.2 |
| S-08 | Provider 不得打印密钥材料或完整明文 | 详细设计 28.3 |
| S-09 | Provider 不得自动从 HSM 降级到 Software | 详细设计 28.3 |
| S-10 | 非幂等操作 UNKNOWN 状态不得自动重试 | 详细设计 32.3 |

### 4.2 密钥状态转换矩阵

| 当前 → 目标 | 条件 | 是否允许 |
|-------------|------|:--------:|
| CREATED → ACTIVE | 激活 | ✓ |
| CREATED → REVOKED | 创建后发现异常 | ✓ |
| CREATED → DESTROYED | 创建失败清理 | ✓ |
| ACTIVE → ROTATED | 新版本产生 | ✓ |
| ACTIVE → DISABLED | 临时禁用 | ✓ |
| ACTIVE → EXPIRED | 系统自动到期 | ✓ |
| ACTIVE → REVOKED | 安全事件/撤销 | ✓ |
| ACTIVE → DESTROYED | 满足销毁条件 | ✓ |
| DISABLED → ACTIVE | 重新激活 | ✓ |
| DISABLED → REVOKED | 永久撤销 | ✓ |
| DISABLED → DESTROYED | 销毁 | ✓ |
| ROTATED → DESTROYED | 满足保留期 | ✓ |
| EXPIRED → DESTROYED | 销毁 | ✓ |
| REVOKED → DESTROYED | 满足销毁条件 | ✓ |
| DESTROYED → 任意 | 终态 | ✗ |
| REVOKED → ACTIVE | 不允许重新激活 | ✗ |
| EXPIRED → ACTIVE | 原则上不得重新激活 | ✗ |
| ROTATED → ACTIVE | 不允许旧版本重新激活 | ✗ |

### 4.3 状态-操作权限矩阵

| 状态 | Encrypt | Decrypt | Sign | Verify | HMAC | Rotate | Destroy |
|------|:-------:|:-------:|:----:|:------:|:----:|:------:|:-------:|
| CREATED | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✓ |
| ACTIVE | ✓* | ✓* | ✓* | ✓* | ✓* | ✓ | ✓ |
| ROTATED | ✗ | ✓* | ✗ | ✓* | ✗ | ✗ | ✓ |
| DISABLED | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✓ |
| EXPIRED | ✗ | 策略 | ✗ | 策略 | ✗ | ✗ | ✓ |
| REVOKED | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✓ |
| DESTROYED | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

`*` 还必须满足 KeyUsage + 授权 + 版本状态 + 安全策略。

### 4.4 双认证模型

| 维度 | 系统管理 API | 对外业务 API |
|------|-------------|-------------|
| 路径前缀 | `/api/v1/admin/**` | `/api/v1/crypto/**`, `/api/v1/keys/**` |
| 认证方式 | JWT Token | AppId + AppSecret (HMAC-SM3 签名) |
| 请求头 | `Authorization: Bearer {token}` | `X-App-Id` + `X-Timestamp` + `X-Nonce` + `X-Signature` |
| 时间戳容差 | — | ≤ 5 分钟 |
| Nonce | — | Redis 去重，防重放 |
| 失败锁定 | 连续 5 次 → 锁定 30 分钟 | 连续 5 次 → 锁定 10 分钟 |

### 4.5 审计哈希链

```
算法：SM3(Log[n] + Hash[n-1]) = Hash[n]
特性：追加写入、不可篡改
存储：sys_audit_log.previous_hash / current_hash
验证：从任意起点重新计算链式哈希，与存储值比对
```

### 4.6 响应格式

```json
{
  "code": 0,           // int 类型，0=成功，非0=错误码
  "message": "success",
  "data": {},
  "requestId": "req-xxxx",
  "timestamp": "2026-09-17T10:30:00.000+08:00"
}
```

### 4.7 幂等控制

必须支持 `Idempotency-Key` 的接口：
- `POST /api/v1/admin/keys`
- `POST /api/v1/admin/keys/{keyId}/rotate`
- `POST /api/v1/admin/keys/{keyId}/destroy`
- `POST /api/v1/admin/auth/token/revoke`

规则：相同 key + 相同 request_hash → 返回原结果；相同 key + 不同 request_hash → 返回 `IDEMPOTENCY_KEY_REUSED`。

### 4.8 数据模型关键约束

- 外键约束不在 DDL 中定义，全部通过 EF Core 应用层校验
- `sys_key.owner_app_id` 存储 `sys_application.app_id`（VARCHAR），非 BIGINT 主键
- `updated_at` 通过 EF Core SaveChanges 拦截器统一维护
- 所有业务 ID（key_id, app_id, device_id, audit_id, event_id）为 VARCHAR(64)
- 枚举值以 VARCHAR 存储，不使用数据库级 ENUM（兼容国产数据库）
- `sys_audit_log.operator_type` 四种值：APP / ADMIN / USER / SYSTEM

## 6. 风险与注意事项

### 6.1 高优先级风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| HSM 厂商 SDK 未到位 | Phase 6 无法启动，阻塞 HSM 全链路验证 | Phase 2-5 使用 SoftwareCryptoProvider 开发；提前冻结厂商型号（详细设计 36.2） |
| 国产数据库 EF Core Provider 不成熟 | Migration 失败或运行时异常 | 先用 MySQL 8.4 开发；在目标数据库尽早做全量验证；保留 Provider 切换能力 |
| SM2 密文/签名格式厂商差异 | HSM 与 Software 加密结果不兼容 | Phase 2 设计时预留 Encoding 参数；联调前确认厂商支持的格式（ASN.1 DER / C1C3C2） |
| SM4-GCM / HMAC-SM3 HSM 支持不确定 | 部分算法可能无法在 HSM 执行 | 设计冻结前确认 HSM 能力（详细设计 36.2 第 4/5 项） |

### 6.2 技术注意事项

| 事项 | 说明 |
|------|------|
| 并发控制 | 密钥轮换/销毁必须使用分布式锁 + SELECT FOR UPDATE 双重保护 |
| 密钥 ID 格式 | 统一使用 `KEY-{ULID}` 格式，确保全局唯一且有序 |
| 审计日志性能 | 审计写入为热路径，考虑批量异步写入（但哈希链必须保持顺序） |
| GCM Nonce 安全 | 同一密钥下 Nonce 绝不重复使用；未提供时由 CSPRNG 生成 |
| 常量时间比较 | HMAC 验签必须使用 `CryptographicOperations.FixedTimeEquals`，防止时序攻击 |
| 内存安全 | Root Key 在内存驻留，进程退出时必须安全清除（内存置零） |
| 密钥库文件保护 | 文件权限 `chmod 600`，不得存放在数据库/Web 可访问/临时目录 |
| 幂等键过期 | `sys_idempotency_record.expires_at` 必须设置，定期清理过期记录 |
| 错误响应 | 外部 API 统一返回平台错误码，不暴露 SQL 异常/HSM SDK 堆栈/数据库连接信息 |
| 时间戳 | 所有时间使用 UTC 存储，API 响应中可带时区偏移 |

### 6.3 开发前必须确认事项（冻结清单）

以下事项必须在联调前确认（来源：详细设计 36.2）：

1. HSM 厂商、型号、SDK 版本

3. HSM 支持的 SM2 签名格式
4. HSM 是否支持 SM4-GCM
5. HSM 是否支持 HMAC-SM3
6. HSM 密钥备份/同步机制
7. 目标国产数据库产品和版本
8. 国产数据库 .NET Provider
9. 国产数据库 EF Core Provider
10. 目标国产 CPU 架构
11. 目标国产操作系统
12. 生产环境是否强制 HSM
13. 大数据流式密码运算接口能力
14. 国密 TLS 接入方式
