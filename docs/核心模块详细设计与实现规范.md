# 1. 完整数据库设计与 DDL

## 1.1 枚举定义

以下枚举值在所有表中以 `VARCHAR` / `TINYINT` 存储，不使用数据库级 `ENUM`，以兼容国产数据库。

```text
-- sys_application.status
-- 0: ACTIVE    正常
-- 1: DISABLED  禁用
-- 2: LOCKED    锁定（安全事件触发）

-- sys_application_secret.status
-- 0: ACTIVE    有效
-- 1: REVOKED   已撤销
-- 2: EXPIRED   已过期

-- sys_key.status / sys_key_version.status (生命周期状态机)
-- CREATED / ACTIVE / ROTATED / DISABLED / EXPIRED / REVOKED / DESTROYED

-- sys_key_version.provider_type
-- HSM / SOFTWARE

-- sys_key_authorization.status
-- ACTIVE / DISABLED / EXPIRED

-- sys_key_authorization.permissions
-- ENCRYPT / DECRYPT / SIGN / VERIFY / HMAC（逗号分隔多值）

-- sys_crypto_device.status
-- ONLINE / DEGRADED / OFFLINE / MAINTENANCE

-- sys_audit_log.operator_type
-- APP / ADMIN / USER / SYSTEM

-- sys_security_event.severity
-- INFO / LOW / MEDIUM / HIGH / CRITICAL

-- sys_security_event.status
-- OPEN / ACKNOWLEDGED / HANDLING / RESOLVED / CLOSED
```

## 1.2 敏感字段标识与存储安全要求

| 表名                   | 敏感字段                          | 安全要求                                                  |
| ---------------------- | --------------------------------- | --------------------------------------------------------- |
| sys_application_secret | secret_hash                       | 存储 KDF/Password Hash 结果（如 PBKDF2），绝不存储明文    |
| sys_key_version        | provider_key_ref                  | Provider 内部不透明引用，不得暴露给外部 API               |
| sys_key_version        | encrypted_key_material            | **高敏感** — 软件模式下经 KEK 加密后的密钥包装材料 |
| sys_user               | password_hash                     | **高敏感** — 加盐哈希存储，不可逆                  |
| sys_audit_log          | previous_hash / current_hash      | 哈希链完整性保护字段，不可修改                            |
| sys_idempotency        | request_hash / response_body_hash | 请求/响应摘要哈希，不存储原始敏感数据                     |

**全局禁止存储项：** HSM 私钥明文、SM4/HMAC 对称密钥明文、AppSecret 明文、Access Token 明文、请求中的明文密码数据、Authorization Header 原始值。

### 关键设计约束

- **主键策略：** 所有表主键采用雪花 ID（Snowflake ID，64 位 long），由应用层 `SnowflakeIdGenerator` 生成，数据库不使用自增（`ValueGeneratedNever()`）
- **外键约束：** 不在 DDL 中定义外键约束，全部通过应用层（EF Core）执行关联校验
- **关联方式：** sys_key.owner_app_id 存储 sys_application.app_id（VARCHAR），非 BIGINT 主键
- **用户角色：** 采用多对多关联（sys_user_role），非单字段 role_id
- **updated_at：** 通过 EF Core SaveChanges 拦截器统一维护，不依赖数据库 ON UPDATE
- **索引总长度：** 需在目标数据库验证，特别是 utf8mb4 下联合索引

## 1.4 国产数据库适配注意事项

| 适配项        | MySQL 8.4                          | 达梦 DM8                            | 人大金仓 KingbaseES          | 注意事项                                                           |
| ------------- | ---------------------------------- | ----------------------------------- | ---------------------------- | ------------------------------------------------------------------ |
| 主键 ID       | `BIGINT NOT NULL`（雪花 ID）    | 雪花 ID（应用层生成）            | 雪花 ID（应用层生成）       | 所有表主键由应用层雪花 ID 生成器分配，不使用数据库自增               |
| datetime 精度 | `DATETIME(6)`                    | `TIMESTAMP(6)` 或 `DATETIME(6)` | `TIMESTAMP(6)`             | 达梦 DATETIME 精度语法需实测；金仓用 TIMESTAMP                     |
| 大字段        | `TEXT` / `LONGTEXT`            | `TEXT` / `CLOB`                 | `TEXT` / `CLOB`          | 达梦大字段建议 CLOB；金仓 TEXT 无长度限制                          |
| JSON 类型     | `JSON`                           | `JSON`（DM8）                     | `JSONB`                    | 金仓 JSONB 性能更优；达梦需确认版本支持                            |
| 索引长度      | utf8mb4 下 VARCHAR(64)=256B        | 字符集下索引总长度限制不同          | PG 规则                      | 联合索引总长度需在实际数据库验证                                   |
| 布尔类型      | `TINYINT(1)`                     | `BIT` / `INT`                   | `BOOLEAN`（实际 SMALLINT） | 统一用 0/1 整数值                                                  |
| ON UPDATE     | `ON UPDATE CURRENT_TIMESTAMP(6)` | 可能不支持                          | 不支持，需触发器             | 建议用 EF Core SaveChanges 拦截器统一维护                          |
| 字符集        | `utf8mb4`                        | `UTF-8`                           | `UTF8`                     | 达梦初始化时指定；金仓创建库时指定                                 |

**关键建议：** 不在 DDL 中使用数据库级外键约束（应用层执行关联校验）；`updated_at` 通过 EF Core 拦截器维护；索引总长度需在实际数据库验证。

# 2. KeyService 完整实现设计

## 2.1 IKeyService 接口定义

> **注意：** 以下为精简后的核心接口。完整代码骨架（含 DTO 定义、异常处理、DI 注册）见 [实现规范-KeyService.md](实现规范-KeyService.md)（第 34 章）。

```csharp
namespace CryptoPlatform.Application.Keys;

public interface IKeyService
{
    Task<KeyDescriptor> CreateAsync(CreateKeyCommand command, CancellationToken ct);
    Task<KeyDescriptor> GetAsync(string keyId, CancellationToken ct);
    Task<KeyDescriptor> ActivateAsync(string keyId, CancellationToken ct);
    Task<KeyDescriptor> RotateAsync(string keyId, RotateKeyCommand command, CancellationToken ct);
    Task DisableAsync(string keyId, CancellationToken ct);
    Task RevokeAsync(string keyId, CancellationToken ct);
    Task DestroyAsync(string keyId, DestroyKeyCommand command, CancellationToken ct);
    Task<KeyVersionDescriptor> GetVersionAsync(string keyId, int versionNo, CancellationToken ct);
    Task<IReadOnlyList<KeyVersionDescriptor>> GetVersionsAsync(string keyId, CancellationToken ct);

```

**与旧版接口差异说明：**

- 命名空间从 `Services` 改为 `Keys`
- 移除 `Backup/Restore/VerifyRestore`（归入独立备份模块）
- 两阶段销毁合并为单一 `DestroyAsync`（内部仍执行申请+确认流程）
- 新增 `GetVersionsAsync` 批量查询版本列表

## 2.2 各操作详细实现设计

### 2.2.1 Create — 密钥创建与补偿事务

```
输入: CreateKeyCommand(AppId, KeyType, KeyUsage, Name, ExpiresAt, Description)
前置校验:
  1. Application.status == ACTIVE
  2. KeyType + KeyUsage 组合合法
  3. Name 非空且长度合规

执行流程（Saga 模式）:
┌─ BEGIN DB Transaction ─────────────────────────────┐
│  1. 生成 KeyId（格式: KEY-{ULID}）                  │
│  2. INSERT sys_key (status=CREATED)                 │
│  3. 生成 ConcurrencyStamp (GUID)                    │
└─ COMMIT ────────────────────────────────────────────┘
         │
         ▼
┌─ Provider 操作（非 DB 事务）─────────────────────────┐
│  4. ICryptoProviderRouter 选择 Provider              │
│  5. Provider.GenerateKeyAsync / GenerateKeyPairAsync │
│  6. 获取 ProviderKeyRef + PublicKey（SM2 场景）       │
│  [失败] → 进入补偿流程                               │
└──────────────────────────────────────────────────────┘
         │
         ▼
┌─ BEGIN DB Transaction ─────────────────────────────┐
│  7. INSERT sys_key_version (status=CREATED)         │
│  8. UPDATE sys_key SET current_version = 1          │
│  9. INSERT sys_audit_log                            │
└─ COMMIT ────────────────────────────────────────────┘
         │
         ▼
返回 KeyDescriptor（含 KeyId, VersionNo=1, PublicKey）

补偿事务处理（Provider 成功、DB 失败）:
  1. 记录 ProviderKeyRef 到补偿任务表
  2. 后台 Worker 重试 DB 写入（最多 3 次，指数退避）
  3. 重试失败 → Provider.DestroyKeyAsync 销毁孤儿密钥
  4. 销毁失败 → 产生 SECURITY_EVENT (CRITICAL)
  5. 绝不将孤儿 ProviderKeyRef 返回给业务系统
```

### 2.2.2 Activate — 密钥激活与 Provider 健康检查

```
┌─ BEGIN DB Transaction（含行锁）──────────────────────┐
│  1. SELECT sys_key FOR UPDATE                        │
│  2. SELECT sys_key_version FOR UPDATE                │
│  3. 校验 Version.Status == CREATED                   │
│  4. Provider.CheckHealthAsync() → 失败则回滚          │
│  5. Provider.GetKeyInfoAsync(ProviderKeyRef)          │
│  6. UPDATE Version.Status = ACTIVE                   │
│  7. UPDATE Key.Status = ACTIVE                       │
│  8. INSERT sys_audit_log                              │
└─ COMMIT ────────────────────────────────────────────┘
Provider 验证失败: 整个事务回滚，Key 保持 CREATED
```

### 2.2.3 Disable — 密钥临时停用

```
┌─ BEGIN DB Transaction（含行锁）──────────────────────┐
│  1. SELECT sys_key FOR UPDATE                        │
│  2. 校验: ACTIVE → DISABLED                          │
│  3. UPDATE sys_key SET status = DISABLED              │
│  4. UPDATE sys_key_version SET status = DISABLED      │
│  5. INSERT sys_audit_log                              │
└─ COMMIT ────────────────────────────────────────────┘
允许后续重新激活（DISABLED → ACTIVE）
```

### 2.2.4 Rotate — 密钥轮换、并发锁控制与版本切换

```
┌─ 获取分布式锁 lock:key-rotate:{KeyId} ──────────────┐
│  ┌─ BEGIN DB Transaction ──────────────────────────┐ │
│  │  1. SELECT sys_key FOR UPDATE                   │ │
│  │  2. 重新读取 current_version（不用客户端值）      │ │
│  │  3. newVersionNo = current_version + 1          │ │
│  │  4. INSERT 新 KeyVersion (CREATED)              │ │
│  └─ COMMIT ────────────────────────────────────────┘ │
│  ┌─ Provider 操作 ─────────────────────────────────┐ │
│  │  5. Provider.GenerateKeyAsync                   │ │
│  │  6. [失败] → 删除新 KeyVersion 记录             │ │
│  └──────────────────────────────────────────────────┘ │
│  ┌─ BEGIN DB Transaction ──────────────────────────┐ │
│  │  7. 新 Version → ACTIVE                         │ │
│  │  8. 旧 Version → ROTATED, rotated_at = NOW      │ │
│  │  9. UPDATE sys_key.current_version              │ │
│  │  10. INSERT sys_audit_log                       │ │
│  └─ COMMIT ────────────────────────────────────────┘ │
│  ┌─ HSM 验证 ─────────────────────────────────────┐ │
│  │  11. 确认新旧 ProviderKeyRef 均可用              │ │
│  └──────────────────────────────────────────────────┘ │
└─ 释放分布式锁 ────────────────────────────────────────┘

并发控制: 分布式锁 + SELECT FOR UPDATE 双重保护
并发请求 B 获取锁后重新读取 current_version，发现已变化 → 返回 KEY_ROTATION_CONFLICT
```

### 2.2.5 Revoke — 密钥永久撤销

```
┌─ BEGIN DB Transaction（含行锁）──────────────────────┐
│  1. SELECT sys_key FOR UPDATE                        │
│  2. 校验: {CREATED, ACTIVE, DISABLED} → REVOKED │
│  3. UPDATE sys_key SET status = REVOKED               │
│  4. UPDATE sys_key_version SET status = REVOKED       │
│  5. INSERT sys_audit_log                              │
└─ COMMIT ────────────────────────────────────────────┘
REVOKED 不可恢复为 ACTIVE
```

### 2.2.6 Expire — 到期自动失效处理

```
触发: 后台 Worker 定时扫描（每分钟）
  1. SELECT sys_key WHERE status=ACTIVE AND expires_at <= NOW()
  2. 批量处理（每批 100 条）:
     UPDATE sys_key SET status = EXPIRED
     UPDATE sys_key_version SET status = EXPIRED
     INSERT sys_audit_log (operator_type = SYSTEM)
  3. 产生 SECURITY_EVENT (severity=MEDIUM)
```

### 2.2.7 Destroy — 两阶段销毁

**第一阶段：申请**

```
  1. 校验权限，生成 DestroyRequestId（有效期 15 分钟）
  2. 记录到缓存: KeyId, OperatorId, Reason, ExpireAt
  3. INSERT sys_audit_log (KEY_DESTROY_REQUEST)
```

**第二阶段：确认**

```
  1. 重新校验 Token + 高权限二次确认
  2. 校验 DestroyRequestId 未过期
  3. UPDATE sys_key SET status = DESTROYED
  4. 遍历所有 KeyVersion:
     Provider.DestroyKeyAsync(ProviderKeyRef)
     记录销毁结果:
       Success → DESTROYED, destroy_result=SUCCESS
       NotFound → 按设备能力映射（能证明不存在则 DESTROYED）
       Failed/Timeout → destroy_result 记录, 产生 SECURITY_EVENT
  5. 验证: GetKeyInfo 确认密钥不存在
  6. 清除 encrypted_key_material
  7. INSERT sys_audit_log (KEY_DESTROYED)
```

### 2.2.8 Import — 安全导入与格式/算法校验

```
  1. 格式校验: SM2 私钥校验 ASN.1 结构; SM4 校验长度==16B; HMAC 校验长度>=32B
  2. 算法校验: KeyType 与材料格式匹配; SM2 校验曲线参数
  3. 创建 Key + KeyVersion (status=CREATED)
  4. 软件模式: KEK 加密后存储; HSM 模式: 安全导入机制注入
  5. 计算指纹 (SM3)
  6. INSERT sys_audit_log (KEY_IMPORTED)
导入后状态: CREATED（禁止跳过 CREATED 直接 ACTIVE）
```

### 2.2.9 Backup — 加密备份

```
  HSM 模式: 调用 HSM 自身备份/密钥同步能力
  软件模式: 读取 encrypted_key_material → 使用 Backup KEK 再次加密 → 返回双层加密数据 + 指纹
  备份数据绝不包含明文密钥材料
```

### 2.2.10 Restore — 恢复与完整性校验

```
  1. Backup KEK 解密外层
  2. 校验指纹 == BackupFingerprint（不匹配 → SECURITY_EVENT）
  3. 校验 KeyId/VersionNo 一致性
  4. DESTROYED 状态拒绝恢复
  5. KEK 重新加密存储，状态 CREATED
  6. INSERT sys_audit_log (KEY_RESTORED)
```

### 2.2.11 VerifyRestore — 恢复后可用性验证

```
  1. 完整性校验: 重新计算指纹比对
  2. Provider.GetKeyInfoAsync 验证可用性
  3. 算法自检:
     SM2 → 签名+验签; SM4 → 加密+解密; HMAC → 生成+验证
  4. 通过 → 允许激活; 失败 → SECURITY_EVENT
  5. INSERT sys_audit_log (KEY_RESTORE_VERIFIED)
```

## 3.2 通用授权校验算法（每次运算前执行）

> **双认证模型：** 系统 API 和管理 API 使用不同认证路径，见 [实现规范-认证授权.md](实现规范-认证授权.md)（第 38 章）。

```
管理 API 路径（/api/v1/admin/**）:
  1. 验证 JWT Token 有效（签名、exp、iss、aud）
  2. Token.OperatorId → 管理用户存在且状态正常
  3. 权限校验（RBAC: 用户角色 → 权限编码匹配）

业务 API 路径（/api/v1/crypto/**, /api/v1/keys/**）:
  1. 验证 AppId + AppSecret 签名（HMAC-SM3）
  2. Request.AppId → Application 存在且 status == ACTIVE
  3. IP 白名单校验

通用密钥授权校验（两条路径共同执行）:
  4. Key 存在（keyId 查询）
  5. 调用方 == Key.OwnerAppId 或存在有效 KeyAuthorization
  6. Key.status 允许当前操作（参照状态-操作矩阵）
  7. 确定 KeyVersion（指定版本 or CurrentVersion）
  8. KeyVersion 存在且状态允许
  9. Key.KeyUsage 与操作匹配
  10. Provider 可用（CheckHealth）
  11. 安全策略允许（配额、限流）
  12. 执行密码运算（通过 ICryptoProvider）
  13. 写入 AuditLog（异步追加）

任何一步失败 → 立即返回错误码，不进入 Provider
```

## 3.3 SM2 运算实现

### 3.3.1 SM2 Encrypt / Decrypt

```
加密:
  - 校验 KeyType==SM2 && KeyUsage==ENCRYPT
  - Plaintext 长度 ≤ 4096 bytes（或按 Provider 能力）
  - 编码格式由 ProviderCapability 声明（ASN.1 DER 默认 / C1C3C2）
  - Provider.EncryptAsync(keyRef, plaintext, {Algorithm=SM2, Encoding})
  - 返回 {KeyId, KeyVersion, Ciphertext, Encoding}

解密:
  - 校验 KeyType==SM2 && KeyUsage==ENCRYPT
  - 允许 ROTATED/EXPIRED 版本解密历史数据
  - Provider.DecryptAsync(keyRef, ciphertext, {Algorithm=SM2, Encoding})
  - 失败统一返回 CRYPTO_DECRYPT_FAILED，不暴露 Padding 细节
```

### 3.3.2 SM2 Sign / Verify

```
签名:
  - 校验 KeyType==SM2 && KeyUsage==SIGN
  - 签名格式: ASN.1 DER（默认）/ Raw(r||s)
  - Provider 内部使用 SM3 计算摘要后签名
  - 返回 {KeyId, KeyVersion, Signature, SignatureFormat}

验签:
  - 校验 KeyType==SM2 && KeyUsage==SIGN
  - ROTATED/EXPIRED 版本允许验签
  - Provider.VerifyAsync → 返回 bool（不抛异常）
```

## 3.4 SM3 运算实现

### 3.4.1 SM3 Hash

```
  - 不涉及密钥，不需要 KeyId
  - Provider.HashAsync(SM3, data)
  - 输出格式: HEX（默认）/ BASE64
  - 支持空数据摘要
  - 大数据流使用分块/流式接口 `Sm3HashStreamAsync`（需求 F-SM3-002）
```

### 3.4.2 HMAC-SM3

```
生成:
  - 校验 KeyType==HMAC && KeyUsage==MAC
  - 密钥通过 keyId 引用，禁止直接上传 HMAC Key
  - Provider.HmacAsync(keyRef, data)
  - 返回 {KeyId, KeyVersion, Mac, MacHex}

验证:
  - Provider.HmacAsync 计算 MAC
  - 使用常量时间比较（ConstantTimeEquals）比对
  - 返回 bool，不暴露比较差异位置
```

## 3.5 SM4 运算实现

### 3.5.1 SM4 ECB

```
  - 校验 ProviderCapability 包含 SM4_ECB
  - Padding: PKCS#7（自动填充）
  - 不推荐生产使用（相同明文产生相同密文），API 文档标注风险
```

### 3.5.2 SM4 CBC

```
  - IV 处理: 请求提供 → 校验长度==16B; 未提供 → CSPRNG 自动生成
  - Padding: PKCS#7（默认）
  - 同一密钥不得重复使用相同 IV
  - IV 随密文返回（解密时需相同 IV）
  - Padding 错误 → CRYPTO_DECRYPT_FAILED，不暴露细节
```

### 3.5.3 SM4 CTR

```
  - Nonce 处理: 请求提供 → 校验长度; 未提供 → CSPRNG 自动生成
  - 不需要 Padding
  - 同一密钥下 Nonce 不得重复
  - 加密和解密使用完全相同的 Nonce
```

### 3.5.4 SM4 GCM（重点）

```
加密:
  - Nonce: 推荐 12 bytes (96 bit); 请求提供则校验长度; 未提供则 CSPRNG 生成
  - AAD: 可选，不加密但参与认证; 解密时必须完全一致
  - Tag: Provider 返回（通常 16 bytes / 128 bit）
  - 返回 {KeyId, KeyVersion, Algorithm, Nonce, Ciphertext, Tag}

解密:
  - 必须提供与加密时完全一致的 Nonce + AAD + Tag
  - Tag 校验失败处理:
    1. 不返回任何部分明文
    2. 记录失败审计日志
    3. 返回 CRYPTO_AUTHENTICATION_FAILED
    4. 不暴露是 Tag 不匹配还是 AAD 不匹配

安全约束:
  - Nonce 重复使用会彻底破坏 GCM 安全性
  - 密文封装建议携带 keyId + keyVersion + algorithm 元数据
```

## 4.1 分层架构与物理隔离

│                      │                                      │

**物理隔离规则：**

- `CryptoPlatform.Crypto.Abstractions` — 仅接口和模型，零外部依赖
- `CryptoPlatform.Crypto.Software` — 依赖 Abstractions + BouncyCastle
- `CryptoPlatform.Crypto.Hsm.VendorX` — 独立项目，依赖 Abstractions + 厂商 SDK
- **业务层只引用 Abstractions 项目**
- 厂商 SDK 的 `using` 只能出现在 Vendor Adapter 项目中

## 4.2 ICryptoProvider 抽象接口

```csharp
namespace CryptoPlatform.Crypto.Abstractions;

public interface ICryptoProvider
{
    string ProviderType { get; }   // "HSM" / "SOFTWARE"
    string ProviderName { get; }   // 实例名称（日志/路由用）

    // 密钥生成
    Task<ProviderKeyResult> GenerateKeyAsync(KeyAlgorithm algorithm, CancellationToken ct);
    Task<ProviderKeyPairResult> GenerateKeyPairAsync(KeyPairAlgorithm algorithm, CancellationToken ct);

    // 加解密
    Task<CryptoResult> EncryptAsync(ProviderKeyReference keyRef, ReadOnlyMemory<byte> plaintext, CryptoParameters parameters, CancellationToken ct);
    Task<CryptoResult> DecryptAsync(ProviderKeyReference keyRef, ReadOnlyMemory<byte> ciphertext, CryptoParameters parameters, CancellationToken ct);

    // 签名/验签
    Task<SignResult> SignAsync(ProviderKeyReference keyRef, ReadOnlyMemory<byte> data, CryptoParameters parameters, CancellationToken ct);
    Task<bool> VerifyAsync(ProviderKeyReference keyRef, ReadOnlyMemory<byte> data, ReadOnlyMemory<byte> signature, CryptoParameters parameters, CancellationToken ct);

    // 杂凑 / MAC
    Task<byte[]> HashAsync(HashAlgorithmName algorithm, ReadOnlyMemory<byte> data, CancellationToken ct);
    Task<byte[]> HmacAsync(ProviderKeyReference keyRef, ReadOnlyMemory<byte> data, CancellationToken ct);

    // 随机数
    Task<byte[]> GenerateRandomAsync(int length, CancellationToken ct);

    // 密钥管理
    Task<ProviderKeyInfo> GetKeyInfoAsync(ProviderKeyReference keyRef, CancellationToken ct);
    Task<ProviderDestroyResult> DestroyKeyAsync(ProviderKeyReference keyRef, CancellationToken ct);

    // 健康检查
    Task<ProviderHealthResult> CheckHealthAsync(CancellationToken ct);

    // 能力声明
    IReadOnlySet<string> GetCapabilities();
}
```

## 4.3 ICryptoProviderRouter 路由机制

```csharp
namespace CryptoPlatform.Crypto.Abstractions;

public interface ICryptoProviderRouter
{
    /// <summary>根据已有密钥版本选择 Provider</summary>
    Task<ICryptoProvider> RouteForExistingKeyAsync(string providerType, long? deviceId, CancellationToken ct);

    /// <summary>为新密钥生成选择 Provider</summary>
    Task<ICryptoProvider> RouteForNewKeyAsync(KeyAlgorithm algorithm, CancellationToken ct);

    /// <summary>获取所有已注册 Provider</summary>
    IReadOnlyList<ICryptoProvider> GetAllProviders();
}
```

**路由优先级：**

1. KeyVersion 已绑定 Provider → 使用绑定 Provider
2. 新建 Key → 使用系统默认 Provider（SystemConfig 配置）
3. 默认 Provider 不可用 → 根据 HA 策略选择备用 Provider
4. **不允许未经策略配置自动把 HSM 密钥转成软件密钥**

## 4.4 Provider 实现边界

| 维度     | HsmCryptoProvider                                    | SoftwareCryptoProvider              |
| -------- | ---------------------------------------------------- | ----------------------------------- |
| 密钥存储 | 密钥在 HSM 内部生成和存储，平台仅持有 ProviderKeyRef | 密钥经 KEK 加密后存储在数据库       |
| 使用场景 | 生产环境                                             | 开发/测试环境，或明确允许的降级场景 |
| 降级策略 | 故障时不自动降级到 Software                          | N/A                                 |
| 销毁方式 | 调用 HSM 销毁接口                                    | 清除数据库中的加密材料              |
| 备份方式 | HSM 自身备份/同步机制                                | 加密备份导出                        |

## 4.5 厂商 SDK 隔离原则（依赖倒置）

```
核心规则: 新增密码机厂商只需新增一个 Adapter 项目，
         绝不修改业务层、Service 层或 API 层代码。

实现方式:
  1. 厂商 Adapter 实现 ICryptoProvider 接口
  2. 通过 DI 注册: services.AddHsmProvider<VendorXAdapter>()
  3. Adapter 内部封装厂商 SDK 调用
  4. 业务层通过 ICryptoProviderRouter 获取 Provider
  5. 业务层代码中不出现任何厂商 SDK 的 using

新增厂商步骤:
  1. 创建 CryptoPlatform.Crypto.Hsm.VendorX 项目
  2. 引用 CryptoPlatform.Crypto.Abstractions
  3. 引用厂商 SDK NuGet/DLL
  4. 实现 VendorXCryptoProvider : ICryptoProvider
  5. 实现 VendorXAdapter（封装 SDK 细节）
  6. 在 DI 注册: services.AddCryptoProvider<VendorXCryptoProvider>()
  7. 在 sys_crypto_device 注册设备信息
  8. 完成。无需修改任何其他项目。
```

## 4.6 Provider 错误码映射

```
统一错误模型（对外）:
  PROVIDER_UNAVAILABLE          密码设备/模块不可用
  PROVIDER_TIMEOUT              调用超时
  PROVIDER_KEY_NOT_FOUND        Provider 中密钥不存在
  PROVIDER_KEY_INVALID          Provider 中密钥无效
  PROVIDER_OPERATION_FAILED     操作执行失败
  PROVIDER_DEVICE_OFFLINE       设备离线
  PROVIDER_AUTH_FAILED          Provider 认证失败
  PROVIDER_CAPABILITY_NOT_SUPPORTED  能力不支持

内部保留厂商原始错误码，外部只返回统一平台错误码。
映射表配置在 Adapter 项目内部，不暴露给业务层。
```

## 4.7 超时控制与重试策略

```
超时层级:
  API Timeout (30s) > Application Service Timeout (15s) > Provider Timeout (5-10s)

重试策略:
  - Hash / Verify 等幂等操作 → 可有限重试（最多 2 次）
  - GenerateKey / DestroyKey / Sign 等非幂等操作 → 禁止自动重试
  - 超时后 → 通过 GetKeyInfo 确认最终状态
  - 无法确认 → 进入 UNKNOWN / 人工核验，不重复执行

连接管理:
  - HSM 连接复用（连接池）
  - 并发控制（不超过 max_concurrent）
  - 不记录密钥材料、不记录完整明文
```

## 4.8 健康检查规范

```
CheckHealthAsync 返回:
  - Status: HEALTHY / DEGRADED / UNHEALTHY
  - LatencyMs: 响应延迟
  - DeviceStatus: 设备状态
  - ErrorMessage: 错误信息（仅异常时）

检查频率:
  - 主动检查: 每次路由前检查设备状态缓存
  - 定时检查: 后台 Worker 每 30 秒执行全量健康检查
  - 被动检查: Provider 调用失败后触发即时检查

状态转换:
  - 连续 3 次健康检查失败 → ONLINE → DEGRADED
  - 连续 5 次失败 → DEGRADED → OFFLINE
  - 恢复后 → OFFLINE → ONLINE（需管理员确认或自动恢复策略）
```

# 6. 认证与授权实现规范

> 本章节提供双认证模型的核心实现设计。完整实现代码见 [实现规范-认证授权.md](实现规范-认证授权.md)（第 38 章）。

## 6.1 双认证模型总览

| 维度     | 系统管理 API                      | 对外业务 API                                                   |
| -------- | --------------------------------- | -------------------------------------------------------------- |
| 路径前缀 | `/api/v1/admin/**`              | `/api/v1/crypto/**`, `/api/v1/keys/**`                     |
| 认证方式 | 用户名/密码 → JWT Token          | AppId + AppSecret → HMAC-SM3 签名                             |
| 凭据存储 | 服务端 JWT 签发                   | 客户端持有 AppId + AppSecret                                   |
| 请求头   | `Authorization: Bearer {token}` | `X-App-Id` + `X-Timestamp` + `X-Nonce` + `X-Signature` |
| 适用场景 | 密钥管理、用户管理、系统配置      | 加密/解密/签名/哈希等密码运算                                  |

## 6.2 管理 API 认证流程

```
客户端: POST /api/v1/admin/auth/token { username, password }
服务端:
  1. 查找 sys_user WHERE username = @username AND status != 禁用
  2. 校验密码哈希（PBKDF2/SM3）
  3. 检查 login_fail_count / locked_until
  4. 签发 JWT Token:
     - sub = operatorId (sys_user.id)
     - aud = "management-api"
     - exp = 配置的过期时间
     - roles = 用户角色列表
  5. 重置 login_fail_count
  6. 返回 { accessToken, expiresIn, tokenType }
```

## 6.3 业务 API 签名认证流程

```
客户端构造签名:
  signatureContent = HTTP_Method + "\n" + Request_Path + "\n" + Timestamp + "\n" + Nonce + "\n" + BodyHash
  signature = HMAC-SM3(appSecret, signatureContent)

服务端校验:
  1. 检查 X-Timestamp 与服务器时间差 ≤ 5 分钟
  2. 检查 X-Nonce 未重复（Redis 缓存）
  3. 根据 X-App-Id 查找 sys_application + ACTIVE 的 sys_application_secret
  4. 用 secret_hash 校验签名（PBKDF2 还原 → HMAC-SM3 计算 → 常量时间比较）
  5. 校验 IP 白名单
  6. 通过 → 设置 HttpContext.User (AppId claim)
```

## 6.4 密钥授权校验器

```csharp
namespace CryptoPlatform.Authorization;

public interface IKeyAuthorizationChecker
{
    Task CheckAsync(string keyId, string operation, string callerAppId, CancellationToken ct);
}
```

校验逻辑：

1. Key 存在且 status 允许当前操作
2. callerAppId == Key.OwnerAppId **或** 存在有效 sys_key_authorization 记录
3. KeyAuthorization.permissions 包含当前 operation
4. KeyAuthorization.status == ACTIVE 且未过期
