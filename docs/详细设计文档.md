# 1. 密钥管理详细设计

## 1.1 设计目标

密钥管理模块是平台的核心安全边界，负责密码学密钥从创建、生成、激活、使用、轮换、禁用、过期、撤销到销毁的全过程管理。

设计原则：

1. 密钥材料不得通过普通业务接口返回。
2. 私钥、SM4 密钥、HMAC 密钥不得离开密码服务平台安全边界。
3. KeyType、KeyUsage、OwnerAppId
   在密钥创建后不可修改；如需变化，创建新密钥。
4. 密钥元数据与密钥材料分离。
5. 密钥版本独立管理，逻辑 KeyId 表示一组版本，KeyVersion
   表示具体密码学材料。
6. 软件密码模块与 HSM 均通过统一 Crypto Provider 抽象。
7. 所有生命周期变化必须产生不可篡改审计记录。
8. 密钥销毁必须具备二次确认、权限校验和销毁结果验证。

## 1.2 密钥对象模型

平台将"逻辑密钥"和"密钥版本"分离。

### 1.2.1 Key

Key 表示业务语义上的逻辑密钥：

- KeyId
- OwnerAppId
- KeyType
- KeyUsage
- Name
- Status
- CurrentVersion
- CreatedAt
- ActivatedAt
- ExpiresAt
- DestroyedAt
- Description

KeyId 在整个生命周期内保持不变。

### 1.2.2 KeyVersion

KeyVersion 表示某一把密钥的具体版本：

- KeyVersionId
- KeyId
- VersionNo
- ProviderType
- ProviderKeyRef
- PublicKeyMaterial（仅 SM2 公钥）
- EncryptedKeyMaterial（软件密码模块场景）
- Fingerprint
- Status
- CreatedAt
- ActivatedAt
- RotatedAt
- ExpiresAt
- DestroyedAt

HSM 场景下，平台数据库保存 ProviderKeyRef，不保存 HSM 内部私钥明文。

## 1.3 密钥类型

| KeyType | 算法             | KeyUsage | 材料                       |
| ------- | ---------------- | -------- | -------------------------- |
| SM2     | SM2              | SIGN     | 公钥 + 私钥                |
| SM2     | SM2              | ENCRYPT  | 公钥 + 私钥                |
| SM4     | SM4-128          | ENCRYPT  | 128 bit 对称密钥           |
| HMAC    | HMAC-SM3         | MAC      | HMAC 密钥                  |
| ROOT    | 平台密钥加密体系 | WRAP     | 根密钥，仅允许安全设备保护 |

APP_SECRET 不纳入密码学 Key 表的实际密钥材料管理，应作为
ApplicationCredential 独立实体管理。

## 1.4 密钥用途约束

KeyUsage 创建后不可修改。

允许关系：

- SM2 + SIGN：仅允许 Sign / Verify。
- SM2 + ENCRYPT：仅允许 Encrypt / Decrypt。
- SM4 + ENCRYPT：仅允许 Encrypt / Decrypt。
- HMAC + MAC：仅允许 HMAC Generate / Verify。

服务层必须同时校验：

`调用方身份 → Key.OwnerAppId → KeyType → KeyUsage → Operation`

其中“调用方身份”在系统管理 API 中为 Token.OperatorId，在对外业务 API 中为 Request.AppId。

任一环节不匹配均拒绝执行。

## 1.5 密钥生成流程

### 1.5.1 SM2

1. API 接收创建请求。
2. AuthenticationService 校验调用方。
3. AuthorizationService 校验 KeyUsage。
4. KeyService 创建逻辑 Key。
5. CryptoProvider 选择 HSM 或软件密码模块。
6. Provider 生成 SM2 密钥对。
7. Provider 返回 ProviderKeyRef 和公钥。
8. KeyService 写入 KeyVersion。
9. 写入审计日志。
10. 返回 KeyId、VersionNo、公钥及元数据。

私钥不返回。

### 1.5.2 SM4

1. 生成 128 bit 随机密钥。
2. 若使用 HSM，则密钥直接在 HSM 内生成。
3. 软件密码模块场景下使用平台密钥包装密钥材料。
4. 数据库存储包装后的密钥材料。
5. 返回 KeyId，不返回明文密钥。

### 1.5.3 HMAC-SM3

HMAC
密钥由密码学安全随机源生成，密钥长度按实际密码库/设备能力配置；需求文档给出的"不低于
256 位"作为平台默认要求。

## 1.6 密钥存储设计

### 1.6.1 HSM 模式

推荐生产模式：

`Application → API → KeyService → CryptoProvider → HSM`

数据库仅保存：

- ProviderType = HSM
- DeviceId
- ProviderKeyRef
- Key fingerprint
- Key metadata

私钥、SM4 密钥和 HMAC 密钥不进入数据库。

### 1.6.2 软件密码模块模式

`Application → API → KeyService → CryptoProvider → SoftwareCryptoProvider`

密钥材料必须使用平台密钥加密体系保护：

`DataKey → Key Encryption Key → Root Key`

实际 Root Key 不得以数据库明文保存。

Root Key 应由 HSM 或经安全评估的软件密钥保护机制管理。生产环境是否允许纯软件 Root Key，应作为部署安全等级的明确配置项，不得以"默认安全"替代实际密码设备要求。

### 1.6.3 无 HSM 场景下的 Root Key 存储方案

当部署环境不具备 HSM 时，Root Key 采用"加密密钥库文件 + 主密码"方式保护：

**1. 密钥库文件（Keystore File）**

- 使用加密密钥库文件存储 Root Key，文件格式采用 PKCS#12 或平台自定义加密格式。
- 密钥库文件使用由主密码（Master Password）经 KDF（如 PBKDF2-HMAC-SM3，迭代次数不低于 600,000 次）派生的密钥进行 SM4-GCM 加密。
- 密钥库文件存储在应用服务器的受保护目录，文件权限设置为仅应用运行用户可读写（如 Linux `chmod 600`）。
- 密钥库文件不得存放在数据库目录、Web 可访问目录或系统临时目录。

**2. 主密码管理**

- 主密码不存储在系统内部，不写入配置文件、环境变量或数据库。
- 主密码由安全管理员保管，系统启动时由管理员通过安全通道（如管理控制台或加密命令行）输入。
- 主密码解锁后，Root Key 在内存中驻留，进程退出或系统关闭时必须安全清除（内存置零）。
- 支持主密码轮换：轮换时需重新加密密钥库文件，旧主密码立即失效。

**3. 密钥库生命周期**

```
系统启动
   ↓
管理员输入主密码
   ↓
KDF 派生保护密钥
   ↓
解密并加载密钥库文件 → Root Key 进入内存
   ↓
系统运行期间：Root Key 在内存中用于加解密 DataKey
   ↓
系统关闭：安全清除内存中的 Root Key
```

**4. 安全约束**

- 密钥库文件损坏或丢失时，所有由其保护的加密密钥材料不可恢复，因此必须执行密钥备份（见 1.10）。
- 密钥库文件备份必须使用独立存储介质，备份传输必须加密。
- 连续主密码输入失败达到阈值（默认 5 次）时，系统拒绝继续尝试并产生安全事件，防止暴力破解。
- 密钥库文件完整性校验：每次加载时必须验证 GCM Tag 或 HMAC，校验失败则拒绝加载并产生安全事件。

**5. 密钥包装层级（无 HSM 完整视图）**

```text
Master Password（管理员保管，不存储于系统）
        ↓ KDF
Protection Key（内存中临时存在）
        ↓ SM4-GCM 加密
Keystore File（受保护文件）
        ↓ 解密后加载
Root Key（内存中驻留）
        ↓ SM4-GCM 包装
KEK（加密后存数据库）
        ↓ SM4-GCM 包装
DataKey / 业务密钥材料（加密后存数据库）
```

**6. 部署安全等级配置**

| 部署场景                 | Root Key 保护方式          | 是否允许       |
| ------------------------ | -------------------------- | -------------- |
| 生产 + HSM               | HSM 内部保护               | 推荐           |
| 生产 + 无 HSM            | 加密密钥库文件 + 主密码    | 需安全评审批准 |
| 开发 / 测试              | 配置文件明文（仅限非生产） | 仅限非生产环境 |
| 生产 + 无 HSM + 无主密码 | 不允许                     | 禁止           |

生产环境是否允许纯软件 Root Key，应作为部署安全等级的明确配置项，不得以"默认安全"替代实际密码设备要求。

## 1.7 密钥状态机

状态：

`CREATED → ACTIVE → ROTATED / DISABLED / EXPIRED / REVOKED → DESTROYED`

其中"使用"不是状态，而是 ACTIVE 状态下允许执行的行为。

### 1.7.1 状态定义

| 状态      | 含义           | 密码操作                                             |
| --------- | -------------- | ---------------------------------------------------- |
| CREATED   | 已生成未启用   | 禁止                                                 |
| ACTIVE    | 当前有效       | 按 KeyUsage 允许                                     |
| ROTATED   | 已被新版本替代 | 默认仅历史解密/验签                                  |
| DISABLED  | 临时停用       | 禁止                                                 |
| EXPIRED   | 超过有效期     | 默认仅历史解密/验签                                  |
| REVOKED   | 永久撤销       | 原则上禁止新的密码操作；历史数据是否允许解密需按策略 |
| DESTROYED | 材料已销毁     | 禁止                                                 |

### 1.7.2 状态转换

| 当前     | 目标      | 条件               |
| -------- | --------- | ------------------ |
| CREATED  | ACTIVE    | 激活权限           |
| CREATED  | REVOKED   | 创建后发现异常     |
| CREATED  | DESTROYED | 创建失败清理       |
| ACTIVE   | ROTATED   | 新版本产生         |
| ACTIVE   | DISABLED  | 临时禁用           |
| ACTIVE   | EXPIRED   | 系统自动到期       |
| ACTIVE   | REVOKED   | 安全事件/撤销权限  |
| ACTIVE   | DESTROYED | 满足销毁条件       |
| DISABLED | ACTIVE    | 重新激活           |
| DISABLED | REVOKED   | 永久撤销           |
| DISABLED | DESTROYED | 销毁               |
| ROTATED  | DESTROYED | 满足保留期         |
| EXPIRED  | DESTROYED | 销毁               |
| REVOKED  | DESTROYED | 满足销毁条件       |

不允许：

- DESTROYED → 任意状态（终态）
- REVOKED → ACTIVE（不允许重新激活）
- EXPIRED → ACTIVE（原则上不得重新激活）
- ROTATED → ACTIVE（不允许旧版本重新成为当前版本）

## 1.8 密钥轮换

轮换采用"逻辑 Key 不变、Version 增加"的方式。

例如：

`KEY-001/V1 → KEY-001/V2`

轮换步骤：

1. 校验当前版本状态。
2. 根据原 Key 的 KeyType、KeyUsage 生成新版本。
3. 新版本完成生成并验证。
4. 新版本 ACTIVE。
5. 旧版本转 ROTATED。
6. 更新 Key.CurrentVersion。
7. 记录审计。
8. 如 Provider 为 HSM，确认新旧 ProviderKeyRef 均可用。

轮换触发条件：

- 到期前轮换；
- 调用次数达到阈值；
- 数据量达到阈值；
- 管理员手工轮换；
- 安全事件触发。

具体阈值通过 SystemConfig 配置。

## 1.9 密钥导入

增加功能：

`F-KM-012 密钥导入`

导入必须区分：

1. 公钥导入；
2. 私钥导入；
3. 对称密钥导入；
4. HSM 密钥迁移。

原则：

- 明文密钥不得通过普通日志、QueryString、URL 传输。
- 导入接口必须使用 TLS。
- 导入操作必须有专门权限。
- 导入后的密钥必须经过算法、长度和格式校验。
- 导入后立即进入 CREATED。
- 禁止直接绕过 CREATED 状态进入 ACTIVE，除非明确配置允许。
- HSM 导入应优先使用 HSM 安全导入机制。

## 1.10 密钥备份与恢复

增加：

- F-KM-013 密钥备份
- F-KM-014 密钥恢复
- F-KM-015 恢复验证

HSM 模式下优先依赖 HSM 自身安全备份/密钥同步能力。

软件密码模块模式下，备份内容必须是加密包装后的密钥材料，不允许导出明文。

恢复后必须执行：

1. 完整性校验；
2. KeyId/Version 一致性校验；
3. 密钥材料解包验证；
4. Provider 可用性验证；
5. 指定算法自检；
6. 审计记录。

# 2. HSM / Crypto Provider 详细设计

## 2.1 Provider 抽象目标

平台业务代码不得直接依赖具体密码机厂商 SDK。

统一抽象：

```text
ICryptoProvider
 ├── HsmCryptoProvider
 └── SoftwareCryptoProvider
```

## 2.2 Provider 接口

核心接口：

```csharp
public interface ICryptoProvider
{
    ProviderType Type { get; }

    KeyGenerationResult GenerateKey(KeyGenerateRequest request);

    KeyGenerationResult GenerateKeyPair(KeyGenerateRequest request);

    byte[] Encrypt(CryptoContext context, byte[] plaintext);

    byte[] Decrypt(CryptoContext context, byte[] ciphertext);

    byte[] Sign(CryptoContext context, byte[] digest);

    bool Verify(CryptoContext context, byte[] digest, byte[] signature);

    byte[] Hash(HashAlgorithmType algorithm, byte[] data);

    byte[] Hmac(HmacAlgorithmType algorithm, byte[] keyRef, byte[] data);

    RandomResult GenerateRandom(int length);

    ProviderKeyInfo GetKeyInfo(string providerKeyRef);

    void DestroyKey(string providerKeyRef);

    ProviderHealth CheckHealth();
}
```

实际项目中不建议让业务层直接传递密钥字节；`keyRef`
应为平台内部密钥引用。

## 2.3 Provider 路由

根据：

- SystemConfig.ProviderMode
- KeyVersion.ProviderType
- DeviceId
- ProviderHealth

选择实际 Provider。

优先级：

1. KeyVersion 已绑定 Provider → 使用绑定 Provider。
2. 新建 Key → 使用系统默认 Provider。
3. 默认 Provider 不可用 → 根据 HA 策略选择备用 Provider。
4. 不允许未经策略配置自动把 HSM 密钥转换成软件密钥。

## 2.4 HSM 设备抽象

建立 CryptoDevice：

- DeviceId
- DeviceName
- Vendor
- Model
- SerialNumber
- Endpoint
- ProviderType
- Status
- Priority
- IsPrimary
- LastHealthCheckAt
- ErrorCount

设备状态：

`ONLINE / DEGRADED / OFFLINE / MAINTENANCE`

支持：

- 注册
- 启用/禁用
- 健康检查
- 主备切换
- 连接池
- 超时
- 故障统计
- 密钥引用检查

## 2.5 HSM 调用安全

HSM 调用层：

`CryptoService → Provider → ConnectionPool → HSM SDK → HSM`

要求：

- 连接复用；
- 调用超时；
- 并发控制；
- Provider 错误码转换；
- 不记录密钥材料；
- 不记录完整明文；
- 对非幂等操作禁止盲目自动重试。

## 2.6 软件 Provider

SoftwareCryptoProvider 用于：

- 开发环境；
- 测试环境；
- HSM 不可用时的明确降级场景（如安全策略允许）。

生产环境默认不允许因 HSM 故障自动降级到软件 Provider 执行原 HSM
密钥操作。

## 2.7 Provider 错误模型

统一：

```text
PROVIDER_UNAVAILABLE
PROVIDER_TIMEOUT
PROVIDER_KEY_NOT_FOUND
PROVIDER_KEY_INVALID
PROVIDER_OPERATION_FAILED
PROVIDER_DEVICE_OFFLINE
PROVIDER_AUTH_FAILED
PROVIDER_CAPABILITY_NOT_SUPPORTED
```

内部保留厂商错误码，外部返回统一平台错误码。

# 3. 数据库详细设计

## 3.1 数据库设计原则

数据库主要保存：

- 身份数据；
- 应用数据；
- 权限数据；
- 密钥元数据；
- Provider 引用；
- 审计数据；
- 安全事件；
- 系统配置。

数据库不得保存：

- HSM 私钥；
- HSM 对称密钥明文；
- API 请求中的明文密码数据；
- Access Token 明文；
- AppSecret 明文。

# 4. API 完整详细设计

## 4.1 API 认证分类

平台 API 按使用场景分为两类，采用不同的认证机制：

### 4.1.1 系统管理 API（Token 认证）

适用对象：系统管理员、密钥管理员、安全审计员等内部管理人员。

认证方式：通过管理控制台或管理接口登录（用户名 + 密码），获取 JWT Access Token，后续请求携带 Bearer Token。

```
管理员 → 登录接口（用户名/密码）→ 获取 JWT Token → Bearer Token 调用管理 API
```

覆盖接口范围：

- 密钥全生命周期管理（创建、激活、轮换、停用、撤销、销毁）
- 应用管理（创建应用、分配 AppSecret、启用/禁用应用）
- 用户与角色权限管理
- 系统配置（Provider 配置、安全策略、轮换策略）
- 审计日志查询与导出
- 安全事件管理
- HSM / 密码设备管理
- 密钥导入 / 备份 / 恢复

特点：

- 必须通过登录流程获取 Token，Token 具有明确有效期。
- Token 内包含操作员身份（OperatorId）、角色、权限范围（scope）。
- 敏感操作（密钥销毁、AppSecret 重置、HSM 配置）必须二次确认。
- Token 支持主动撤销（Redis 保存 revoked jti）。

### 4.1.2 对外业务 API（应用凭据认证）

适用对象：接入平台的第三方业务系统。

认证方式：通过 appId + appSecret 进行请求签名认证，无需登录获取 Token。

```
第三方系统 → 携带 appId + 签名 → 服务端校验签名 → 执行密码业务
```

覆盖接口范围：

- SM4 加密 / 解密
- SM2 加密 / 解密 / 签名 / 验签
- SM3 哈希
- HMAC-SM3 生成 / 校验
- 随机数生成

特点：

- 第三方系统无法进行登录交互，因此不要求 Token 认证。
- 每次请求通过 appId + appSecret 对请求参数进行签名，服务端验签。
- 签名同时保证请求完整性和身份认证，防止篡改和伪造。

### 4.1.3 应用凭据签名认证流程

**1. 凭据组成**

每个接入应用分配：

- `appId`：应用唯一标识，明文传输。
- `appSecret`：应用密钥，仅在创建时展示一次，之后不可找回，只能重新生成。appSecret 不直接传输，而是参与签名计算。

**2. 签名算法**

采用 HMAC-SM3 对请求内容进行签名：

```text
待签名内容 = HTTP Method + "\n"
           + Request Path + "\n"
           + Timestamp + "\n"
           + Nonce + "\n"
           + BodyHash（请求体的 SM3 哈希，Base64 编码）

Signature = Base64(HMAC-SM3(appSecret, 待签名内容))
```

**3. 请求头构造**

```http
X-App-Id: {appId}
X-Timestamp: {unix_timestamp}
X-Nonce: {nonce}
X-Signature: {signature}
Content-Type: application/json
X-Request-Id: {request_id}
```

**4. 服务端校验流程**

```
1. 提取 X-App-Id，查询 Application 记录
2. 检查 Application 状态是否为 ACTIVE
3. 检查 IP 白名单（如已配置）
4. 检查 Timestamp 偏差（默认允许 ±5 分钟）
5. 检查 Nonce 是否已使用（Redis 防重放，默认有效期 10 分钟）
6. 根据 appId 获取 appSecret（数据库仅存哈希，需使用相同算法重新计算比对）
7. 使用相同算法计算签名并比对
8. 校验通过 → 进入授权与业务处理
9. 任一环节失败 → 拒绝请求，记录安全事件
```

**5. 安全约束**

- Timestamp + Nonce 防重放，与 Token 认证模式要求一致。
- appSecret 连续认证失败达到阈值（默认 5 次 / 10 分钟）时，锁定该应用并产生安全事件。
- 锁定后需管理员通过管理控制台手动解锁。
- appSecret 支持轮换，轮换期间旧版本保持短暂有效（默认 24 小时），保证第三方系统平滑切换。

# 5. 认证与凭据详细设计

> 平台采用双认证模型：系统管理 API 使用 Token 认证，对外业务 API 使用应用凭据签名认证。本章分别描述两种认证机制的凭据设计。

## 5.1 双认证模型总览

| 维度         | 系统管理认证               | 对外业务认证              |
| ------------ | -------------------------- | ------------------------- |
| 适用对象     | 管理员、密钥管理员、审计员 | 第三方业务系统            |
| 凭据         | 用户名 + 密码              | appId + appSecret         |
| 认证方式     | 登录获取 JWT Token         | 请求签名（HMAC-SM3）      |
| Token 有效期 | 2 小时（可配置）           | 无 Token，每次请求签名    |
| 凭据存储     | 密码哈希（服务端）         | appSecret 哈希（服务端）  |
| 撤销机制     | Token 撤销（Redis jti）    | 应用禁用 / appSecret 重置 |
| 接口范围     | 管理 API                   | 密码业务 API              |

## 5.2 AppSecret 生命周期

`CREATED → ACTIVE → EXPIRED / REVOKED`

AppSecret 在对外业务认证中作为签名密钥使用，不参与 Token 获取流程。

支持：

- 创建；
- 激活；
- 轮换；
- 撤销；
- 过期；
- 失败锁定。

AppSecret 不可找回。

## 5.3 AppSecret 存储

AppSecret 采用不可逆哈希存储：

`secret → KDF/Password Hash → secret_hash`

数据库不得保存原文。

若系统存在必须向管理员展示一次的场景，仅在创建成功时展示一次，之后只能重新生成。

轮换时旧版本保持短暂有效（默认 24 小时），保证第三方系统平滑切换。

## 5.4 Token JWT（系统管理专用）

Token 仅用于系统管理 API 认证，第三方业务系统不使用 Token。

JWT 至少包含：

```json
{
  "iss": "kms-platform",
  "sub": "user-001",
  "aud": "management-api",
  "jti": "token-id",
  "iat": 1770000000,
  "exp": 1770007200,
  "operatorId": "user-001",
  "role": "SYSTEM_ADMIN",
  "scope": [
    "key:manage",
    "app:manage",
    "audit:read"
  ]
}
```

签名算法由平台安全配置统一确定。

## 5.5 Token 校验（系统管理专用）

管理 API 每次请求：

1. 验证签名；
2. 验证 exp；
3. 验证 nbf（如使用）；
4. 验证 iss；
5. 验证 aud；
6. 验证 operatorId；
7. 检查用户状态与角色权限；
8. 检查 scope；
9. 检查 KeyAuthorization；
10. 检查请求时间戳和 Nonce。

## 5.6 对外业务认证校验（应用凭据签名）

业务 API 每次请求：

1. 提取 appId，查询 Application 记录；
2. 检查 Application 状态；
3. 检查 IP 白名单；
4. 检查 Timestamp 偏差；
5. 检查 Nonce 防重放；
6. 校验签名（HMAC-SM3）；
7. 检查 KeyAuthorization；
8. 检查 KeyUsage 与 Operation 匹配；
9. 检查 Provider 可用；
10. 执行密码运算；
11. 写入 AuditLog。

## 5.7 Token 撤销（系统管理专用）

JWT 本身具有无状态特性，因此"立即撤销"必须增加状态机制。

采用：

- Access Token 短生命周期；
- Redis 保存 revoked jti；
- 高风险操作额外检查 Token 状态。

Redis Key：

`token:revoked:{jti}`

TTL 不超过 Token 剩余有效期。

## 5.8 管理员认证

管理控制台采用独立认证体系，与对外业务 API 认证完全隔离。


敏感操作：

- 密钥销毁；
- AppSecret 重置；
- 用户权限变更；
- HSM 配置；
- Root Key 操作；

必须二次确认。

# 6. 审计与安全事件详细设计

## 6.1 审计对象

必须审计：

1. 密码运算；
2. 密钥生命周期；
3. 应用管理；
4. AppSecret；
5. Token；
6. 用户登录；
7. 权限变化；
8. Provider/HSM；
9. 系统配置；
10. 安全策略；
11. 审计自身操作。

## 6.2 Operator 模型

必须增加：

```text
OperatorType:
APP
ADMIN
USER
SYSTEM
```

示例：

`APP/app-demo`

`ADMIN/user-001`

## 6.3 RequestId / TraceId

请求进入 API Gateway 时生成 RequestId。

所有下游服务透传：

`API → Auth → Authorization → KeyService → CryptoProvider → Audit`

保证一条密码操作可关联完整链路。

## 6.4 审计哈希链

写入顺序：

```text
Log[n]
  ↓
SM3(Log[n] + Hash[n-1])
  ↓
Hash[n]
```

每个审计分区维护前置哈希。

周期性生成检查点：

`CheckpointHash`

更高安全等级下，对检查点执行数字签名并存储到独立介质。

## 6.5 审计不可篡改

数据库应用账号：

- 禁止 UPDATE 审计记录；
- 禁止 DELETE 审计记录。

审计员：

- 只读。

管理员：

- 不得修改审计原始记录。

数据库管理员直接操作数据库属于基础设施安全边界问题，需要通过数据库审计、权限分离和不可篡改存储进一步保护。

## 6.6 安全事件

典型事件：

- AppSecret 连续认证失败；
- 管理员连续登录失败；
- 单应用异常高频调用；
- 大量解密；
- 大量签名；
- 密钥用途异常；
- HSM 离线；
- Provider 连续失败；
- 审计哈希链校验失败；
- 权限异常变化；
- 大量密钥销毁；
- IP 白名单违规。

事件流程：

`Detect → Event → Alert → Handle → Close`

# 7. HA / 灾备详细设计

## 7.1 应用层

采用无状态部署：

```text
LoadBalancer
   ↓
API Node 1
API Node 2
API Node N
```

Session 不保存在本地。

## 7.2 Redis

Redis 用于：

- Token 撤销；
- Nonce；
- 限流；
- 分布式锁；
- 短期缓存。

Redis 故障时：

- 密码核心操作不得依赖 Redis 才能完成；
- Token 撤销和防重放必须根据安全策略决定 fail-close；
- 不得因缓存故障绕过授权。

## 7.3 数据库

数据库采用主备/集群架构。

要求：

- 主节点故障自动或人工切换；
- 数据复制；
- 备份；
- 恢复验证。

## 7.4 HSM

推荐至少双设备：

```text
CryptoProvider
 ├── HSM-A Primary
 └── HSM-B Standby
```

关键要求：

- 密钥引用可恢复；
- HSM 状态监控；
- 主备设备能力一致；
- 不允许在故障切换时自动降低安全等级。

## 7.5 故障场景

故障            处理

---

API 节点故障    LB 摘除
Redis 故障      集群切换
DB 主节点故障   DB HA 切换
HSM-A 故障      HSM-B 接管
网络故障        路由/连接切换
单机房故障      灾备中心接管

## 7.6 RTO / RPO

继承需求目标：

- RTO ≤ 30 分钟；
- RPO ≤ 5 分钟。

密钥恢复必须额外执行密钥材料完整性验证，不能只验证数据库备份成功。

# 8. 国产化部署详细设计

## 8.1 部署原则

平台采用：

`应用服务 + 数据库 + Redis + HSM/密码设备`

最终生产部署不依赖 Docker 作为必要条件。

## 8.2 国产化适配矩阵

需要在项目实施阶段形成实际版本矩阵：

| 分类    | 项目                        | 适配要求           |
| ------- | --------------------------- | ------------------ |
| CPU     | x86/ARM64                   | 实际环境确认       |
| OS      | 麒麟/统信等                 | 实际版本确认       |
| Runtime | .NET                        | 与目标 OS/CPU 匹配 |
| DB      | 国产数据库/MySQL/PostgreSQL | 实际驱动确认       |
| Redis   | 国产环境可部署版本          | 实际版本确认       |
| HSM     | 国密密码设备                | 厂商 SDK/接口确认  |
| Web     | Nginx/Apache 等             | 实际版本确认       |
| Browser | Chrome/Edge/国产浏览器      | 管理端验证         |

## 8.3 时间同步

平台所有节点必须使用统一 NTP。

时间同步影响：

- JWT exp；
- AppSecret 过期；
- Key 过期；
- Nonce 防重放；
- Audit Timestamp。

# 13. 密钥管理可编码级详细设计

> 本章在第1章基础上继续细化到实体约束、事务边界、并发控制、幂等和异常处理，作为后续 .NET 10 / EF Core 10 实现依据。具体数据库 Provider 差异仍以实际国产数据库版本验证结果为准。

## 13.1 Key 与 KeyVersion 的关系约束

一个逻辑 Key 对应一个或多个 KeyVersion：

```text
sys_key
   |
   +-- V1 CREATED -> ACTIVE -> ROTATED
   |
   +-- V2 CREATED -> ACTIVE
   |
   +-- V3 CREATED
```

约束：

1. `sys_key.key_id` 全局唯一且不可复用。
2. `sys_key_version.version_no` 在同一 `key_id` 下从 1 开始递增。
3. 同一个逻辑 Key 同时最多只能存在一个当前 ACTIVE 版本。
4. `sys_key.current_version` 必须与 ACTIVE 版本一致。
5. KeyVersion 不允许跨 Key 移动。
6. KeyType、KeyUsage、OwnerAppId 不允许在版本表中覆盖逻辑 Key 的定义。
7. 销毁 Key 时必须处理其全部版本；不能只删除当前版本。
8. 删除采用逻辑状态控制，不提供普通业务级物理 DELETE。

## 13.2 密钥创建事务

### 13.2.1 事务边界

密钥创建包含两个层次：

```text
业务事务：创建 Key 元数据 + 创建 KeyVersion 元数据
安全设备事务：Provider/HSM 生成实际密钥材料
```

HSM/Provider 操作通常不能与数据库事务组成同一个 ACID 事务，因此采用“补偿事务”设计。

### 13.2.2 创建流程

```text
BEGIN DB Transaction
    |
    |-- 校验 App
    |-- 校验 KeyType/KeyUsage
    |-- 创建 sys_key(CREATED)
    |
COMMIT
    |
    v
Provider.GenerateKey()
    |
    +----失败----> 标记 Key/Version 为 REVOKED 或执行失败清理
    |
    v
Provider 返回 ProviderKeyRef/PublicKey
    |
BEGIN DB Transaction
    |
    |-- 创建 KeyVersion
    |-- 更新 sys_key.current_version
    |-- 写入审计
    |
COMMIT
    |
    v
返回 KeyId/VersionNo/PublicKey
```

不允许在 Provider 失败后把数据库记录伪装成 ACTIVE。

### 13.2.3 Provider 成功、数据库失败

这是必须处理的异常场景：

```text
HSM 已生成 V1
       |
       +-- DB 写入失败
       |
       v
补偿任务发现 orphan ProviderKeyRef
       |
       +-- 重试数据库落库
       |
       +-- 无法恢复则执行 Provider.DestroyKey
       |
       +-- 记录 SECURITY_EVENT
```

HSM 密钥引用必须具备可追踪的 correlation/request 标识，但不得把私钥材料写入日志。

## 13.3 激活事务

激活必须使用数据库行锁或等价的并发控制，避免两个管理请求同时激活同一 Key。

```text
BEGIN
  SELECT Key FOR UPDATE
  SELECT Version FOR UPDATE
  校验 Version.Status == CREATED
  校验 Key.Status != DESTROYED/REVOKED
  Provider.GetKeyInfo/HealthCheck
  Provider 自检
  UPDATE Version.Status = ACTIVE
  UPDATE Key.Status = ACTIVE
  UPDATE Key.CurrentVersion = VersionNo
  INSERT AuditLog
COMMIT
```

如果 Provider 验证失败，整个激活操作失败，数据库状态保持 CREATED。

## 13.4 轮换并发控制

同一 Key 的轮换必须串行化。

推荐锁键：

```text
lock:key-rotate:{KeyId}
```

或者使用数据库：

```sql
SELECT id, current_version
FROM sys_key
WHERE key_id = :keyId
FOR UPDATE;
```

轮换必须重新读取 `current_version`，不能使用客户端提交的旧 VersionNo 直接计算新版本。

并发请求：

```text
Request A -> V1 -> 创建 V2
Request B -> 同时读取 V1

A 获得锁 -> V2 ACTIVE -> current_version=2
B 获取锁 -> 重新读取 current_version=2
         -> 发现请求条件已变化
         -> 返回 KEY_ROTATION_CONFLICT 或幂等结果
```

## 13.5 销毁详细设计

销毁属于高风险操作，不允许通过普通删除接口实现。

### 13.5.1 两阶段销毁

第一阶段：申请销毁。

```text
POST /api/v1/keys/{keyId}/destroy-request
```

产生一次性 `DestroyRequestId`，记录：

- KeyId
- OperatorId
- Reason
- RequestTime
- ExpireAt
- RiskLevel
- ConfirmationRequired=true

第二阶段：确认销毁。

```text
POST /api/v1/keys/{keyId}/destroy-confirm
```

确认时再次进行：

1. Token 校验；
2. 高权限校验；
3. DestroyRequestId 校验；
4. 请求未过期；
5. Key 当前状态校验；
6. Provider 销毁；
7. Provider 销毁结果验证；
8. 数据库状态更新；
9. 写入不可篡改审计。

### 13.5.2 Provider 销毁结果

Provider 必须至少返回：

```text
Success
NotFound
NotSupported
Failed
Timeout
```

`NotFound` 不能直接等同于“成功销毁”。如果设备能够证明对象不存在，可按设备能力映射为已销毁；否则必须进入人工核验状态。

## 13.6 密钥轮换后的历史数据处理

轮换后：

- 新数据默认使用新 ACTIVE 版本；
- 历史密文必须保留其版本信息；
- 解密接口不能只接受 KeyId 后盲目使用当前版本；
- 推荐密文元数据携带 `KeyId + VersionNo`；
- 若调用方只提交 KeyId，服务端默认当前版本，但历史数据应明确指定 VersionNo。

推荐密文封装：

```json
{
  "version": 1,
  "keyId": "KEY-001",
  "keyVersion": 3,
  "algorithm": "SM4-GCM",
  "nonce": "...",
  "ciphertext": "...",
  "tag": "...",
  "aad": "..."
}
```

该封装中的 `keyId/keyVersion/algorithm` 属于元数据，不是密钥材料。

# 14. Crypto Provider 可编码级设计

## 14.1 分层结构

```text
API Layer
   |
CryptoApplicationService
   |
ICryptoProviderRouter
   |
ICryptoProvider
   +-------------------------+
   |                         |
HsmCryptoProvider     SoftwareCryptoProvider
   |                         |
Vendor Adapter          国密软件密码模块
   |
HSM SDK
```

业务服务禁止出现如下代码：

```csharp
VendorHsmSdk.GenerateKey(...);
VendorHsmSdk.Sign(...);
```

厂商 SDK 只能出现在独立 Adapter 项目中。

## 14.2 推荐接口

```csharp
public interface ICryptoProvider
{
    string ProviderType { get; }

    Task<ProviderKeyResult> GenerateKeyAsync(
        KeyGenerateRequest request,
        CancellationToken cancellationToken);

    Task<ProviderKeyPairResult> GenerateKeyPairAsync(
        KeyPairGenerateRequest request,
        CancellationToken cancellationToken);

    Task<CryptoResult> EncryptAsync(
        CryptoOperationRequest request,
        CancellationToken cancellationToken);

    Task<CryptoResult> DecryptAsync(
        CryptoOperationRequest request,
        CancellationToken cancellationToken);

    Task<SignResult> SignAsync(
        SignRequest request,
        CancellationToken cancellationToken);

    Task<bool> VerifyAsync(
        VerifyRequest request,
        CancellationToken cancellationToken);

    Task<HashResult> HashAsync(
        HashRequest request,
        CancellationToken cancellationToken);

    Task<MacResult> HmacAsync(
        MacRequest request,
        CancellationToken cancellationToken);

    Task<RandomResult> GenerateRandomAsync(
        RandomRequest request,
        CancellationToken cancellationToken);

    Task<KeyInfoResult> GetKeyInfoAsync(
        string providerKeyRef,
        CancellationToken cancellationToken);

    Task DestroyKeyAsync(
        string providerKeyRef,
        CancellationToken cancellationToken);

    Task<ProviderHealthResult> CheckHealthAsync(
        CancellationToken cancellationToken);
}
```

## 14.3 ProviderKeyRef

`ProviderKeyRef` 是平台内部的“不透明引用”，业务层不得解析其内容。

示例仅用于说明形式：

```text
hsm://device/{device-id}/key/{opaque-id}
```

实际生产格式由厂商 Adapter 决定。

禁止：

- 在 API 中让调用方自行构造 ProviderKeyRef；
- 将 ProviderKeyRef 当作密码学密钥；
- 将 ProviderKeyRef 直接作为外部 KeyId；
- 将厂商 SDK 对象序列化进入数据库。

## 14.4 Capability 设计

Provider 启动后注册能力：

```text
SM2_SIGN
SM2_VERIFY
SM2_ENCRYPT
SM2_DECRYPT
SM2_SIGN_DER
SM2_SIGN_RAW
SM2_CIPHER_C1C3C2
SM2_CIPHER_C1C2C3
SM4_ECB
SM4_CBC
SM4_CTR
SM4_GCM
SM3
HMAC_SM3
RANDOM
KEY_GENERATE
KEY_IMPORT
KEY_DESTROY
KEY_BACKUP
```

API 层在执行前检查 Capability。

这样可以避免把某一台 HSM 支持的格式错误地认为所有 HSM 都支持。

## 14.5 超时和重试

Provider 调用必须有明确超时：

```text
API Timeout
    > Application Service Timeout
        > Provider Timeout
```

推荐原则：

- Hash、Verify 等纯查询/计算操作在确认无副作用时可有限重试；
- GenerateKey、DestroyKey、ImportKey、Sign 等涉及设备状态变化的操作禁止无条件自动重试；
- 超时后必须通过 GetKeyInfo/操作查询能力确认最终状态；
- 无法确认最终状态时进入 UNKNOWN/人工核验，而不是重复执行。

## 15.4 Application 与 Secret

`sys_application` 负责应用身份，`sys_application_secret` 负责凭据生命周期。


这样不会要求业务系统在同一时刻完成强制切换。

# 18. API 事务与幂等设计

## 18.1 幂等键

以下操作必须支持 `Idempotency-Key`：

- Key 创建；
- Key 轮换；
- Key 导入；
- Key 撤销；
- Key 销毁申请；
- Key 销毁确认；
- AppSecret 创建/轮换；
- Token 撤销。

`Idempotency-Key` 应与 AppId、接口路径绑定：

```text
IdempotencyScope = AppId + HTTP Method + Path + Idempotency-Key
```

不能允许一个 App 的幂等键影响另一个 App。

## 18.2 幂等记录

建议建立：

```text
sys_idempotency_record
```

核心字段：

- id
- app_id
- idempotency_key
- request_hash
- response_code
- response_body_hash
- status
- created_at
- expires_at

相同幂等键但请求体不同必须返回冲突错误，而不是执行第二次操作。

## 18.3 错误分类

统一分成：

```text
AUTH_xxx
PERMISSION_xxx
KEY_xxx
CRYPTO_xxx
PROVIDER_xxx
DEVICE_xxx
VALIDATION_xxx
SYSTEM_xxx
AUDIT_xxx
```

对外错误信息不得暴露：

- HSM 内部错误堆栈；

- 私钥状态；
- Padding 详细失败位置；
- Provider SDK 内部路径；

# 19. SM4-GCM 详细接口约束

SM4-GCM 请求必须明确：

```json
{
  "keyId": "KEY-001",
  "keyVersion": 2,
  "plaintext": "SGVsbG8=",
  "nonce": "...",
  "aad": "...",
  "encoding": "base64"
}
```

响应：

```json
{
  "keyId": "KEY-001",
  "keyVersion": 2,
  "algorithm": "SM4-GCM",
  "nonce": "...",
  "ciphertext": "...",
  "tag": "...",
  "encoding": "base64"
}
```

### 19.1 Nonce

如果由调用方提供 Nonce，平台必须校验长度及策略；如果由平台生成，应使用密码学安全随机源。

GCM 模式必须避免同一密钥下 Nonce 重复。平台不能仅依赖数据库随机字符串生成器。

### 19.2 AAD

AAD 不加密，但参与认证。解密时必须使用完全一致的 AAD，否则验签失败。

### 19.3 Tag

Tag 校验失败必须：

1. 不返回任何部分明文；
2. 记录失败审计；
3. 返回统一 `CRYPTO_AUTHENTICATION_FAILED`；
4. 不暴露具体校验位置。

# 20. SM2 详细设计约束

SM2 必须把以下三个概念分开：

1. 曲线/算法参数；
2. 签名编码格式；
3. 密文编码格式。

其中签名可能涉及：

```text
ASN.1 DER
R||S
```

密文可能涉及：

```text
C1C3C2
C1C2C3
```

平台 API 不应根据“SM2”字符串自行转换，而应由 Provider Capability 明确支持范围。

在实际 HSM/软件密码模块接入后，必须建立兼容性测试矩阵：

| Provider | Sign | Verify | Encrypt | Decrypt | Signature Format | Cipher Format |
| -------- | ---- | ------ | ------- | ------- | ---------------- | ------------- |
| HSM-A    | 实测 | 实测   | 实测    | 实测    | 实测             | 实测          |
| HSM-B    | 实测 | 实测   | 实测    | 实测    | 实测             | 实测          |
| Software | 实测 | 实测   | 实测    | 实测    | 实测             | 实测          |

未实测项目不得在正式接口文档中承诺支持。

# 21. 密钥使用计量与轮换策略

如果需求启用“按次数/数据量轮换”，KeyVersion 必须增加使用计量模型。

推荐逻辑字段：

```text
operation_count
processed_bytes
last_used_at
```

但不建议每次密码运算直接更新主 KeyVersion 行，否则高并发下会形成热点行。

推荐：

```text
Crypto Operation
      |
      +--> Audit Event
      |
      +--> Metrics Counter
                 |
                 +--> threshold evaluation
```

超过阈值后产生 `KEY_ROTATION_REQUIRED` 安全事件，由轮换任务处理。

关键点：阈值触发是“需要轮换”的状态，不应在普通密码运算请求中直接同步执行轮换，以免造成业务请求长时间阻塞。

# 25. 开发级数据模型与事务设计

## 25.1 核心实体关系

平台密钥模型采用“逻辑 Key + KeyVersion + KeyAuthorization”三级关系：

```text
Application
    │
    ├──< Key
    │      │
    │      ├──< KeyVersion
    │      │       └── ProviderKeyRef
    │      │
    │      └──< KeyAuthorization >── Application
    │
    └──< ApplicationSecret
```

设计约束：

1. `Key` 是业务标识，不直接表示某一份密码学材料。
2. `KeyVersion` 表示实际可执行密码运算的密钥版本。
3. 一个逻辑 Key 同一时刻原则上只有一个 `ACTIVE` 当前版本。
4. `CurrentVersion` 必须与实际 ACTIVE 版本一致。
5. `OwnerAppId` 创建后不可修改。
6. `KeyType`、`KeyUsage` 创建后不可修改。
7. 授权关系不得改变 Key 的 Owner。
8. 被授权 Application 只能在授权有效期及允许操作范围内使用 Key。
9. `DESTROYED` 表示密码学材料已完成销毁，不允许恢复。

业务层不得出现：

```csharp

```

密码材料只能作为 Provider 内部调用参数存在。

## 26.2 CreateAsync 事务边界

密钥创建属于“外部安全设备 + 数据库”组合操作，不能简单依赖单个数据库事务。

推荐流程：

```text
BEGIN
  创建 Key CREATED
COMMIT

Provider.Generate
   │
   ├──成功
   │
   ▼
保存 KeyVersion
   │
   ▼
激活
   │
   ▼
Audit
```

如果 Provider 生成成功但数据库保存失败：

1. 不允许直接重试生成导致产生未知孤儿密钥。
2. 将 ProviderKeyRef 写入安全补偿任务。
3. 后台执行 Provider Destroy。
4. 销毁失败产生 `SECURITY_EVENT`.
5. 不得把该 ProviderKeyRef 返回业务系统。

## 26.3 RotateAsync

轮换必须防止两个并发请求同时创建 V2。

数据库层采用：

```text
SELECT Key
FROM sys_key
WHERE key_id = ?
FOR UPDATE
```

或者使用 EF Core 对应的乐观并发机制。

逻辑：

```text
锁定 Key
  ↓
读取 CurrentVersion
  ↓
VersionNo = CurrentVersion + 1
  ↓
Provider.Generate
  ↓
保存新 Version
  ↓
新 Version ACTIVE
  ↓
旧 Version ROTATED
  ↓
更新 CurrentVersion
  ↓
提交
```

同一个 Key 同时只能存在一个轮换事务。

## 26.4 DestroyAsync

销毁采用二阶段确认：

```text
第一阶段：申请销毁
        ↓
检查权限
        ↓
记录 Destroy Request
        ↓
第二阶段：确认销毁
        ↓
Provider.Destroy
        ↓
验证 GetKeyInfo/状态
        ↓
数据库标记 DESTROYED
        ↓
写审计
```

销毁请求必须具备：

- KeyId
- VersionNo 或全部版本
- 操作人
- RequestId
- DestroyReason
- ConfirmToken
- ConfirmedAt

`ConfirmToken` 不得直接记录在审计日志中。

## 28.3 Provider 禁止事项

Provider 实现不得：

- 打印密钥材料；
- 打印完整明文；
- 将私钥写入普通临时文件；
- 将 HSM 密钥导出到数据库；
- 在异常中返回密钥内容；
- 为 HSM 密钥自动降级到 SoftwareProvider；
- 在未知执行结果时自动重复执行非幂等操作。

# 29. 密钥访问授权算法

每次密码运算必须执行以下检查，根据 API 类型分为两条认证路径：

**系统管理 API 路径（Token 认证）：**

```text
1. Token 有效（签名、有效期、iss、aud）
2. Token.operatorId 有效，用户状态正常
3. 用户角色/权限允许当前操作
4. Key 存在
5. Key Owner 或显式授权
6. Key 状态允许当前操作
7. KeyVersion 存在
8. KeyVersion 状态允许当前操作
9. KeyUsage 与 Operation 匹配
10. Provider 可用
11. 安全策略允许
12. 执行密码运算
13. 写入 AuditLog
```

**对外业务 API 路径（应用凭据签名认证）：**

```text
1. appId 有效，Application 状态 ACTIVE
2. IP 白名单通过
3. Timestamp 偏差在允许范围内
4. Nonce 未重复使用
5. 签名校验通过（HMAC-SM3）
6. Key 存在
7. Key Owner 或显式授权
8. Key 状态允许当前操作
9. KeyVersion 存在
10. KeyVersion 状态允许当前操作
11. KeyUsage 与 Operation 匹配
12. Provider 可用
13. 安全策略允许
14. 执行密码运算
15. 写入 AuditLog
```

任何检查失败均不得进入 Provider。

## 29.1 状态与操作矩阵

| 状态      | Encrypt |  Decrypt | Sign |   Verify | HMAC | Rotate | Destroy |
| --------- | ------: | -------: | ---: | -------: | ---: | -----: | ------: |
| CREATED   |      否 |       否 |   否 |       否 |   否 |     否 |      是 |
| ACTIVE    |     是* |      是* |  是* |      是* |  是* |     是 |      是 |
| ROTATED   |      否 |      是* |   否 |      是* |   否 |     否 |      是 |
| DISABLED  |      否 |       否 |   否 |       否 |   否 |     是 |      是 |
| EXPIRED   |      否 | 策略决定 |   否 | 策略决定 |   否 |     是 |      是 |
| REVOKED   |      否 |       否 |   否 |       否 |   否 |     否 |      是 |
| DESTROYED |      否 |       否 |   否 |       否 |   否 |     否 |      否 |

`*` 还必须满足 KeyUsage、授权、版本状态和安全策略。

# 30. 密钥包装体系详细设计

## 30.1 软件密码模块

推荐逻辑：

```text
Root Key
   │
   ▼
KEK
   │
   ▼
Encrypted Key Material
   │
   ▼
Database
```

实际密钥材料：

```text
SM4/HMAC/SM2 Private Key
        ↓
DEK/Data Key
        ↓
KEK 加密
        ↓
数据库保存 Wrapped Material
```

Root Key 不得直接作为普通业务 Key 使用。

## 30.2 HSM 模式

```text
Database
 └── ProviderKeyRef
        │
        ▼
CryptoProvider
        │
        ▼
HSM
 └── Actual Key Material
```

业务 API 永远只接收：

```text
keyId
```

而不是：

```text
privateKey
symmetricKey
```

# 31. API 请求对象最终设计

## 31.1 创建密钥

```json
{
  "keyType": "SM4",
  "keyUsage": "ENCRYPT",
  "name": "业务数据加密密钥",
  "expiresAt": "2027-09-17T00:00:00Z",
  "description": "业务系统数据加密"
}
```

返回：

```json
{
  "code": "0",
  "message": "success",
  "data": {
    "keyId": "KEY-xxxxxxxx",
    "versionNo": 1,
    "keyType": "SM4",
    "keyUsage": "ENCRYPT",
    "status": "CREATED"
  },
  "requestId": "REQ-xxxxxxxx",
  "timestamp": "2026-09-17T09:00:00Z"
}
```

不返回：

- SM4 明文密钥；
- HMAC 明文密钥；
- SM2 私钥；
- Root Key；
- HSM PIN；
- Provider 内部认证信息。

## 31.2 SM4-GCM

请求：

```json
{
  "keyId": "KEY-001",
  "plaintext": "SGVsbG8=",
  "encoding": "BASE64",
  "mode": "GCM",
  "nonce": "MTIzNDU2Nzg5MDEy",
  "aad": "YXBwLW1ldGE="
}
```

返回：

```json
{
  "ciphertext": "...",
  "nonce": "...",
  "tag": "...",
  "encoding": "BASE64"
}
```

Nonce 不得重复用于同一密钥。

## 31.3 大数据

对于大文件/大报文，不建议把完整内容长期驻留在普通 JSON 字符串中。

应提供：

```text
初始化 → 分块处理 → 完成
```

接口模型：

```text
POST /api/v1/crypto/sm4/encrypt/sessions
POST /api/v1/crypto/sm4/encrypt/sessions/{id}/chunks
POST /api/v1/crypto/sm4/encrypt/sessions/{id}/complete
```

具体流式接口应在目标 HSM/Provider 确认支持后确定。

# 32. 并发、幂等与补偿

## 32.1 幂等接口

以下接口必须支持 `Idempotency-Key`：

```text
POST /keys
POST /keys/{id}/rotate
POST /keys/{id}/destroy
POST /auth/token/revoke
POST /applications/{id}/secrets/rotate
```

## 32.2 幂等记录

建议：

```text
idempotency_key
app_id
request_hash
response_code
response_body
status
created_at
expires_at
```

相同 Idempotency-Key：

- request_hash 相同：返回原结果；
- request_hash 不同：返回 `IDEMPOTENCY_KEY_REUSED`。

## 32.3 Provider UNKNOWN

HSM 网络超时不等于执行失败。

例如：

```text
请求 Sign
   ↓
HSM 已执行
   ↓
响应丢失
   ↓
平台收到 Timeout
```

此时状态必须定义为：

```text
UNKNOWN
```

对于非幂等操作不得自动重试。

# 33. 异常模型

统一错误结构：

```json
{
  "code": "KEY_NOT_FOUND",
  "message": "密钥不存在或不可用",
  "requestId": "REQ-001",
  "timestamp": "2026-09-17T09:00:00Z"
}
```

外部 API 不返回：

- SQL 异常；
- HSM SDK 原始堆栈；
- Provider 路径；
- 数据库连接信息；
- 密钥内容；
- Padding 内部异常细节。

内部日志通过 `RequestId + TraceId` 关联详细异常。

# 34. 最终项目代码分层

建议 .NET 10 项目结构：

```text
src/
├── CryptoPlatform.Api
├── CryptoPlatform.Application
├── CryptoPlatform.Domain
├── CryptoPlatform.Infrastructure
├── CryptoPlatform.Persistence
├── CryptoPlatform.Crypto
│   ├── Abstractions
│   ├── Hsm
│   └── Software
├── CryptoPlatform.Authentication
├── CryptoPlatform.Authorization
├── CryptoPlatform.Audit
├── CryptoPlatform.Security
└── CryptoPlatform.Worker
```

职责：

- `Domain`：Key、KeyVersion、状态和业务规则；
- `Application`：UseCase/Service；
- `Persistence`：EF Core；
- `Infrastructure`：缓存抽象（ICacheService）与分布式锁（IDistributedLock），支持内存（开发）和 Redis（生产）两种实现；
- `Crypto`：Provider；
- `Hsm`：具体厂商适配器；
- `Authentication`：AppSecret/Token；
- `Authorization`：Key授权；
- `Audit`：审计；
- `Security`：安全事件与策略；
- `Worker`：轮换、过期、补偿、告警。

禁止：

```text
Api → HSM SDK
Api → DbContext
Controller → 厂商密码机
```

必须：

```text
Api
 ↓
Application
 ↓
Domain / Infrastructure
 ↓
CryptoProvider
 ↓
HSM
```

# 36. 当前设计冻结项与待确认项

## 36.1 可以冻结

以下设计可以作为开发基线：

- Key/KeyVersion 分离；
- KeyId 生命周期不变；
- KeyType/KeyUsage/Owner 创建后不可修改；
- HSM/Software Provider 统一抽象；
- 普通 API 不返回密码学私钥或对称密钥；
- Owner + 显式授权模型；
- 生命周期状态机；
- AuditLog 不可篡改；
- 双认证模型：系统管理 API 使用 Token 认证，对外业务 API 使用 appId + appSecret 签名认证；
- 无 HSM 场景下 Root Key 采用加密密钥库文件 + 主密码保护；
- Provider 不自动从 HSM 降级 Software；
- 非幂等 UNKNOWN 不自动重试。

1. HSM 厂商、型号、SDK；

5. HMAC-SM3 是否支持；

7. 国产数据库产品和版本；
8. .NET Provider；
9. EF Core Provider；
10. 国产 CPU；
